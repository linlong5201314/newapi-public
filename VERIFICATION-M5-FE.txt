Deliberate deviations / notes
  1. POST /api/node/test is not implemented by M5-BE. The wizard still requires
     a test attempt: it calls the endpoint first, then falls back to a browser
     GET {serviceUrl}/api/status. A missing endpoint or CORS rejection yields a
     warning (not a hard block); a reachable-but-failing result blocks save.
     The backend's create path already performs a health check, and the UI runs
     an additional POST /api/node/:id/check after creation.
  2. There is no deploy status endpoint. M5-BE deploy/apply is synchronous
     (internal Railway polling up to NodeDeployPollTimeoutSeconds) and returns
     deployment_status. The dialog therefore shows an elapsed-time progress
     state during apply and renders the returned status; it does not poll a
     nonexistent endpoint. getNodeDeployStatus remains as an optional
     compatibility helper but is not used by the dialog.
  3. The listed "CF token/KV namespace/zone" fields map to M5-BE
     cloudflareApiToken / cloudflareKvNamespaceId / cloudflareZoneId. Two extra
     fields were added because the live backend requires them: primaryDomain
     (NodePrimaryDomain, required before any failover plan) and
     cloudflareAccountId (required with the KV namespace for KV updates).
  4. The node wizard exposes the task-listed fields only. M5-BE additionally
     stores workspace_id/environment_id/repo/branch/target_port/service_domain;
     the table displays service_domain and last_error read-only, but editing
     those advanced deployment fields is not included. Consequence: one-click
     deploy of a brand-new Railway project needs either recorded ProjectId+
     ServiceId or a repo configured outside this wizard (M5-BE requires repo when
     ServiceId is empty).
  5. Settings section is registered under System Settings -> Operations (root
     inherited from the system-settings route guard), with a direct "Node
     settings" shortcut from the node page.

Fail-soft behavior verified by code paths:
  - GET /api/node failure -> ErrorState with retry + "backend may not be
    deployed" hint; page never crashes.
  - GET /api/node/settings failure -> defaults + warning; save attempts the API.
  - deploy/failover plan/apply failures -> inline alerts, no state mutation.
  - audit failure -> inline ErrorState inside the drawer.
  - unknown/missing fields -> normalizers degrade to empty values, not throws.
