# 注册与部署踩坑总账（Railway 多节点 new-api + 面板自动换号）

> 建立于 2026-11-15。每条都带「现象 / 根因 / 修法 / 复现命令」，照这个查，别再从零试。
> 环境：Windows 本机面板（`D:\控制面板总结聊天\panel`，8787）+ Go fork（`new-api/`）+ Supabase pooler + CF 只做 DNS。

## 0. 一句话版

- Node 必须 `dns.setDefaultResultOrder('ipv4first')`，否则 Railway GraphQL 走 IPv6 死路。
- Railway 服务源仓库写**短格式** `owner/repo`；`ServiceInstanceUpdateInput` **没有 branch 字段**。
- 域名 `targetPort` 交给 Railway 自动探测（写死 3000/5001 会 502）。
- Cloudflare 代理会限速大文件到 ~2.2 KB/s → 前端必须直连 Railway，CF 只留 DNS。
- Railway 新号 workspace 级风控只在**部署 mutation**里报错，UI/GraphQL 没有布尔字段。
- Supabase 5432 是 session pooler，多节点会把连接打满（`EMAXCONNSESSION`）→ 扩节点前换 6543。

## 1. 面板（Node 侧）

### 1.1 `fetch failed` / `HTTP 429` 一堆
- 现象：`[billing] … 刷新失败: fetch failed`、`[watch] … HTTP 429`，注册脚本启动即 429。
- 根因：Node 22 默认 `dns.getDefaultResultOrder() === 'verbatim'`，`backboard.railway.app` 有 AAAA（`2606:4700::6812:1835`），本机 IPv6 不通 → 每条请求先吃 10s 超时，重试叠加把限流打满。
- 修法：`index.js` 与 `src/railway.js` 顶部
  ```js
  const dns = require('node:dns');
  dns.setDefaultResultOrder('ipv4first');
  ```
  所有独立脚本（`_slow-signup-loop2.mjs`、`_fetch-vars.mjs`）顶部同样加一份。
- 验证：`node -e "const dns=require('node:dns');console.log(dns.getDefaultResultOrder())"` → `ipv4first`；修复后同 token 请求 2s 内 200。

### 1.2 429 无限重试
- 修法：`gql()` 先 `res.text()` 再解析，识别 `try again in ([\d.]+)\s*seconds` 写入 `err.retryAfterMs`；`scheduler.js` 用 `rlUntil` 闸门整段暂停；`pollSeconds` 默认 120（30 太密，7 账号 × 30s 必被限）。

### 1.3 一个面板进程都别多开
- 现象：删掉的账号又出现、`data/accounts.json` 被覆盖。
- 根因：每个进程各自持有账号快照并回写。
- 修法：只留一个监听 8787 的进程；`keeper.cmd` + 计划任务 + 注册表 Run 三保险只负责“拉起来”，不负责“多开”。
- 检查：`Get-NetTCPConnection -LocalPort 8787 -State Listen | Select OwningProcess`。

### 1.4 长注册被 undici 掐断
- 现象：`SIGNUP 0 {"ok":false,"error":"fetch failed"}`，时间恰好 5 分 06 秒。
- 根因：undici 默认 `headersTimeout=300000`。
- 修法：注册脚本里的 `http()` 改用 `node:http`，并把 `req.setTimeout` 传值前做 `Number.isFinite(ms) && ms>0 ? ms : 900000`（传 `null` 会 `ERR_INVALID_ARG_TYPE`）。

### 1.5 data/accounts.json 的格式
- 必须是**数组** `[]`。写成 `{"accounts":[]}` 会得到 `TypeError: accountsCol.load(...).map is not a function`。
- 沙箱里重装面板时尤其容易踩：先 `echo "[]" > data/accounts.json`。

## 2. 面板（浏览器侧）

### 2.1 登录页没有邮箱框
- 现象：`signup-no-form`，页面只有 GitHub / Google 按钮。
- 根因：Railway 默认收起邮箱登录，要点底部 `Log in using email` 才展开。
- 修法：`ensureEmailForm(page,{timeoutMs:30000})` 轮询点击，再查 `input[type="email"]`。

### 2.2 GitHub 绑定状态读不到
- 现象：`bound:null`，`gh-disconnect` 被跳过。
- 根因：账号页改成「卡片 + 右上角 Options 三点菜单（Radix `[role=menu]`）」。
- 修法：`readGithubBindState` 识别 `Connected as <user>`；解绑走 `disconnectGithubViaMenu`；换号前 `releaseOtherGithubBindings`。

### 2.3 WebRTC 泄漏真实 IP
- 修法：`--force-webrtc-ip-handling-policy=disable_non_proxied_udp`；自检 `WEBRTC_CANDIDATE_IPS []`。
- 时区/语言/插件要与出口 IP 自洽：CDP `Emulation.setTimezoneOverride` **必须保活会话**，detach 即还原。

## 3. Railway GraphQL

### 3.1 仓库源必须短格式
- 现象：`Repository "https://github.com/CJackHwang/ds2api" not found or is not accessible`。
- 修法：`input:{source:{repo:'CJackHwang/ds2api'}}`；参照生产服务 `source.repo` 就是 `linlong5201314/newapi-public`。

### 3.2 `ServiceInstanceUpdateInput` 没有 `branch`
- 报错：`Field "branch" is not defined by type "ServiceInstanceUpdateInput"`。
- 可用字段：`source`、`builder`（`HEROKU|NIXPACKS|PAKETO|RAILPACK`，**没有 DOCKERFILE**）、`dockerfilePath`、`rootDirectory`、`buildCommand`、`startCommand`、`healthcheckPath`、`restartPolicyType`、`region`、`numReplicas`。

### 3.3 域名 targetPort 写死 → 502
- 现象：部署 SUCCESS、日志显示 `bind=0.0.0.0:8080`（ds2api）或 3000，域名一律 502。
- 根因：`targetPort` 写死与容器实际端口不一致；主实例的 `targetPort` 是 `null`（自动探测）。
- 修法：
  ```graphql
  mutation { serviceDomainUpdate(input:{domain,environmentId,serviceDomainId,serviceId,targetPort:null}) }
  ```
  四个字段少一个就报 `Field "…" of required type "String!" was not provided`。
- 验证：`serviceDomains.targetPort` + 直接 `/api/status` 200。

### 3.4 必填 selection set
- `serviceDomainCreate` / `serviceDomainUpdate` 必须带返回字段，否则 `must have a selection of subfields`。

### 3.5 部署 500 不一定是真失败
- `POST /api/deploy` → `Problem processing request`，但项目/服务/域名其实已建。判成败要读 `GET /api/accounts/:id/projects` 或 `rw.serviceInstance` + 探 `/api/status`。

### 3.6 位置参数 vs 对象
- `rw.variables(token, projectId, environmentId, serviceId)`、`rw.domains(token, projectId, environmentId, serviceId)`、`rw.serviceDelete(token, id, environmentId)` 都是**位置参数**；传对象会报 `Variable "$projectId" got invalid value {...}`。

### 3.7 workspace 级风控（关键）
- 原文：`We limited this workspace after detecting unusual activity. Upgrade to a paid plan to lift this restriction automatically.`
- 特征：注册成功、建项目成功，**只有部署被拒**；`Workspace` 类型没有 `restricted` 布尔，UI 不显示横幅；`meta.blocked` 也可能为空。
- 假风控：`You are creating projects too quickly. This workspace allows 1 project per 30 seconds.` 是节流，等 30s 即可。
- 判断法：`serviceInstanceDeploy` 报上面那句 = 真风控；`projectCreate` 只报节流 = 还能用。
- 处置：不要立刻删号（删了就没法核对）；保留 `row.kept=true`，把原始报错存 `_evidence/`。

## 4. 入口与 Cloudflare

### 4.1 CF 代理会把大文件掐死
- 实测：5.3MB 主包经 CF `172.67.129.124` 90s 只下 199,799 B（≈2.2 KB/s）；`104.21.2.172` 90s 0 字节；同文件直连 Railway 2.73s（1.9 MB/s）。
- 结论：前端资源不能走 CF 代理/Worker/Static Assets，否则必白屏。
- 正解：CF 只做 **DNS-only CNAME**；`gw.ailong.love → z06s5r7j.up.railway.app`，证书 Let's Encrypt，`/` 1.7s、主包 2.78s。

### 4.2 Worker 自定义域与 DNS 冲突
- 现象：`81062 A DNS record managed by Workers already exists on that host`。
- 修法：先删 Worker custom domain，再改 DNS 记录：
  ```
  DELETE /accounts/{acc}/workers/domains/{id}
  ```
  OAuth token 在 `%APPDATA%\xdg.config\.wrangler\config\default.toml` 的 `oauth_token`（CF API token 只有 zone 级权限，`/accounts` 返回空）。

### 4.3 Railway 自定义域要 TXT 验证
- `verificationDnsHost: "_railway-verify.<sub>"` + `railway-verify=<token>`；建完 `certificateStatus` 才会转 VALID。

### 4.4 `certificateStatus` 与 `verificationToken` 的字段位置（自省出来的）

- `verificationToken` / `verificationDnsHost` / `dnsRecords` 都在 **`CustomDomainStatus`** 上，
  不在 `DNSRecords` 上。查 `DNSRecords { verificationToken }` 会直接报
  `Cannot query field "verificationToken" on type "DNSRecords"`。
- `DNSRecords.recordType` 是枚举：**`DNS_RECORD_TYPE_CNAME` / `DNS_RECORD_TYPE_TXT`**。
  用 `=== 'CNAME'` 永远匹配不到，必须用 `/CNAME$/` 或全名。
- `verificationToken` 的字符串**已经带** `railway-verify=` 前缀，写 TXT 时原样写，再加一次前缀会导致验证失败。
- 归属验证通过后证书还要 2–4 分钟才从 `VALIDATING_OWNERSHIP` 转 `VALID`；期间探测是
  `ERR_TLS_CERT_ALTNAME_INVALID`（拿到的是 Railway 默认证书），不是解析错。
## 5. 数据面（Supabase）

- 现象：871 日志 `FATAL: (EMAXCONNSESSION) max clients reached in session mode`。
- 根因：`SQL_DSN` 用的 5432 session pooler，每节点连接池独占会话。
- 修法：换 6543 transaction pooler，并加 `default_query_exec_mode=simple_protocol`；否则节点越多越挤。
- 直连 `db.xxx.supabase.co` 是 IPv6-only，Railway `ipv6EgressEnabled:false` → 只能 pooler。

## 6. 临时算力盒（instabox）

- 免费套餐 **1 台** 限额：`quota_exceeded … sandbox limit reached (1 of 1)`，先 `ls` 复用已有盒子。
- 起法：`INSTABOX_API_KEY=ibk_… npx instabox@latest ls --json` / `exec <id> -- '<cmd>'` / `push <id> ./dir /data/dir --all` / `pull <id> /path ./local`。

- 盒子里跑本面板：`push` 面板（不含 `data/`）→ `npm i --omit=dev`（6s）→ `PORT=8787 node index.js`（会打印 `powershell: not found`，无害）→ 先 `echo "[]" > data/accounts.json`。

## 十二、小浣熊 / 书生：能不能反代（2026-11-16 实测）

### 12.1 结论
| 来源 | 官方 API？ | 平台怎么接 | 状态 |
|---|---|---|---|
| 书生 InternLM | **有**，OpenAI 兼容 `https://internlm.intern-ai.org.cn/api/v1` | `authMode=key`：用户填官方 Token（`…/api/tokens` 生成），平台只存 key | 模板已上线，`/v1/models` 实测 401 `A0211 user token expired`（路径正确，缺真 key） |

### 12.2 xhx2api 容器（deploy/xhx）
- `Dockerfile`：构建期 `git clone --depth 1 https://github.com/haoxinyu1/xiaohuanxiong2api /up` → `WORKDIR /up/src` → `go build -o /out/xhx2api ./cmd/xhx2api`；运行层 debian-slim + jq。

## 十三、邮箱验证码通道：发不出去的真正原因（2026-11-16 实测）

### 13.1 症状
页面点「发送验证码」一直转圈或直接报错；`/api/reset_password` 30 秒超时无响应。

### 13.2 根因（两条，缺一都发不出去）
1. **只有 438 一台带 `MAIL_OUTBOX_MODE=1`**，842/196/850/733/964/871 全缺 → 请求落到这些节点时 `service/email.go` 的 `MailOutboxSink == nil`，走「直连 SMTP」分支；而 Railway 免费实例封禁出站 465/587，`smtp.qq.com` 连接一直挂着直到超时。用户看到的转圈就是这个。
2. `ServerAddress` 选项为空 → 重置密码邮件里的链接是 `http://localhost:3000/user/reset?...`，点开必失败。

### 13.3 修复动作（已执行）
- 6 台节点补 `MAIL_OUTBOX_MODE=1`（`variableUpsert` + `serviceInstanceDeploy`），438 原已有。
- DB `options` 表写入 `ServerAddress=https://gw.ailong.love`。注意 `PUT /api/option/` **只改当前进程内存**（GET 仍返回空），必须落库后把 7 台统一重部署一次才都生效。
- 面板新增自检端点 `GET http://127.0.0.1:8787/api/mail/health`：返回 IMAP 能否登录、SMTP host/port、最近 5 封 outbox 状态。
- 面板只允许**单实例**：本次又发现 8787 与 9787 各一个实例，已杀掉 9787，只留 8787。

- new-api 只负责把邮件写进 `mail_outbox` 表；真正投递由**常驻面板** `src/mailer.js`（每 20s 扫一次、最多重试 3 次）用 QQ SMTP 直连发送。所以「面板没开 → 验证码发不出」，这也是面板必须常驻的原因之一。
- QQ 授权码 `dkashdiowphddaia` 同时用于 IMAP 收码（注册流水线读验证码）与 SMTP 发码，共用一份，存 `data/settings.json` 的 `mailbox.passEnc`（AES 加密）。
- 注册只允许 QQ 邮箱：`EmailDomainRestrictionEnabled=true` + `EmailDomainWhitelist=qq.com`，其它域名直接 `EMAIL_ADDRESS_REJECTED`。

## 十四、文档推送的隐形陷阱：`_push-root.mjs` 只认 `new-api/` 下的文件

### 14.1 现象
`node _push-root.mjs deploy/注册与部署踩坑总账.md` 打印 `200 … 0d8e1aaa DONE`，看起来成功，但 GitHub 上的文档始终是旧版（2843 B），本地已写到 16 KB；`§十二`、`§十三` 明明写了却查不到。

### 14.2 根因
`_push-root.mjs` 的路径映射是「本地 `new-api/<rel>` → 仓库 `<rel>`」（因为仓库根就等于 Go 工程根）。传 `deploy/xxx.md` 时它实际读的是 `new-api/deploy/xxx.md` 那份旧副本，推上去 sha 不变（`0d8e1aaa` 一直是旧文件），于是出现「返回 200 但内容没变」的假成功。

### 14.3 定规
- 代码（`model/ controller/ web/ …`）继续用 `_push-root.mjs`，因为源在 `new-api/` 下。
- **文档与仓储根文件用 `_push-any.mjs`**：`node _push-any.mjs <本地路径> [仓库路径] [commit消息]`，按传入路径直接读、直接 PUT，并打印 `REMOTE_BEFORE` 与 `LOCAL=B`，可用大小对比立刻识别假成功。
- 判真假成功的唯一标准：`GET /contents/<path>?ref=master&cb=<ts>` 读回内容大小/关键字，不看 PUT 的 200。
